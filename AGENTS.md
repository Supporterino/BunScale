# Project rules

Tauri v2 app, **mobile first, desktop second**. Rust backend (`src-tauri/`), React + TypeScript + Vite frontend (`src/`), TanStack Router + Query.

## Platforms

| Platform | Status |
|---|---|
| iOS | Phase 1, primary |
| macOS | Phase 1 |
| Android, Windows, Linux | Later. No work now, but keep code `cfg`-clean so they stay possible. |

Requires macOS with Xcode. Agents run on a Mac.

## Mobile-first rules

1. Design and build at 390×844 first, then scale up to desktop (1280×800).
2. One route tree for all form factors. Layout adapts (bottom tabs → sidebar), routes do not fork.
3. Touch is baseline; hover, right-click and keyboard shortcuts are progressive enhancement on `pointer: fine`.
4. Platform-specific behavior is declared in the spec scenario (`[ios]`, `[macos]`, `[desktop]`, `[mobile]`) and gated in code with `cfg` (Rust) or a platform helper (TS).

## Source of truth

- **What:** `openspec/`. Never implement without an approved change. Skill `openspec-workflow`.
- **Where:** Graphify graph. Query before grepping. Skill `graphify-usage`.
- **How:** skills in `.opencode/skills/`. Load those listed in your agent file before writing code.

## Layout

```
src-tauri/src/ipc/        commands, events, shared types (contract surface)
src-tauri/src/            domain logic, state, errors
src-tauri/capabilities/   permissions (tauri-security owns)
src-tauri/plugins/        custom Swift plugins (apple-native owns)
src/routes/               TanStack Router file routes
src/features/<name>/      feature code (components, hooks, queries, api.ts)
src/components/ui/        design-system primitives
src/bindings.ts           GENERATED from Rust. Never edit.
src/routeTree.gen.ts      GENERATED by router plugin. Never edit.
docs/adr/                 architecture decisions
.artifacts/screens/       UI screenshots for review (gitignored)
```

## Hard rules

1. **Gate:** a task is done only when every stage of `definition-of-done` whose condition holds passes. The orchestrator runs it and never trusts a specialist's claim.
2. **Contract first:** IPC is defined by `architect` before Rust or frontend implementation. Frontend never calls `invoke` directly; only generated bindings via `src/features/*/api.ts`.
3. **Generated files are read-only.** Regenerate, never edit. Regeneration leaves no diff.
4. **One task = one commit.** `feat(<change-id>): <task>`.
5. **Scope:** edit only paths your agent owns. Out-of-scope need → report to orchestrator.
6. **No new dependencies** without a one-line justification in `design.md`. Plugins must support iOS and macOS.
7. **Ambiguity:** do not guess. Append to `openspec/changes/<id>/questions.md`, mark task blocked, continue with unblocked tasks.
8. **Security:** capabilities, CSP, scopes, entitlements and permission strings change only via `tauri-security`.
9. **Retry limit:** 3 fix loops per task, then stop with a blocker note.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- The commit hook refreshes the graph automatically, and that dirty `graphify-out/` is expected: nobody reviews or diffs it. Do not run `graphify update .` mid-task — refresh at change boundaries (after `openspec archive`, or after a large move).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
