One task = one commit = one owner. Format: `- [ ] <n>.<m> [agent] <imperative>`.
Order: contract → platform bridges and security → backend → frontend-logic → frontend-ui → tests → review.
Tick a task only after the `definition-of-done` gate passes for it.

- [ ] 1.3 [architect] Decide and record the medication occurrence derivation (D4.2): occurrences computed from the medication's P5 schedule for every type that schedules doses, with no second schedule interpreter, and no occurrence for a medication that is not active.
- [ ] 1.4 [architect] Decide and record follow-up evaluation (D4.3): schedule-ahead plus cancel-on-evidence and reconciliation on launch/foreground, with no background mode requested, and state the accepted limitation for a device that never runs the product again.
- [ ] 1.5 [architect] Decide and record the export generation path and file boundary (D4.4/D4.9): Rust-side document generation, the device-local export location and file lifetime, the handoff to the device's standard sharing options, the rejected native-renderer alternative, and that export reads through P0's read path without a gate of its own.

## 2. Backend (Rust)

- [ ] 2.1 [rust-backend] Implement the device-local reminder store: one place holding both kinds outside the household collection, each reminder carrying its kind, target, schedule (where the kind has one), creating member, follow-up flag and enabled state, surviving a relaunch and never written into household data (D3, REM-2).
- [ ] 2.2 [rust-backend] Implement the recurring weigh reminder: a per-rabbit or household-wide target with a user-defined recurring schedule, plus create, edit, disable, enable and delete, each change re-scheduling the reminder (REM-1).
- [ ] 2.3 [rust-backend] Implement reminder scoping: a reminder belongs to the person and device that created it, never notifies another member's device, is unaffected by another member's reminders or their changes, and does not follow the person to another device (REM-2).
- [ ] 2.4 [rust-backend] Implement the weigh missed-reminder follow-up: enabled per reminder, exactly one follow-up raised on the following day when no weight entry was logged for the target since the occurrence fired, suppressed when a weigh-in was logged, and none raised when the follow-up is disabled (REM-3, D4.3).
- [ ] 2.5 [rust-backend] Implement medication occurrence derivation from P5's schedule for every type that schedules doses, raised on the device that configured the reminder, with no occurrence for a medication that is not active (MED-9, D4.2).
- [ ] 2.6 [rust-backend] Implement the medication missed-dose follow-up, enabled by default per medication reminder: exactly one follow-up when a window passes with no dose recorded for it, none when the follow-up is disabled, none when a dose was recorded for the window (MED-10).
- [ ] 2.7 [rust-backend] Implement the as-needed exclusion: a `prn` medication creates no reminder and schedules no occurrence, with or without a maximum-per-day hint, while its doses remain recordable on demand (MED-11).
- [ ] 2.8 [rust-backend] Implement snooze and record-from-reminder: snooze defers the occurrence without recording anything and leaves the slot unsatisfied; the record action opens P5's pre-filled dose confirmation, and the confirmed dose satisfies the occurrence and raises nothing further (MED-9).
- [ ] 2.9 [rust-backend] Implement occurrence reconciliation on launch and foreground return against P0's loaded-data read path: mark occurrences satisfied when their evidence exists, cancel their follow-ups, and never cancel based on data that was not loaded (REM-3, MED-10, D4.3).
- [ ] 2.10 [rust-backend] Implement the export selection for a rabbit and a selected range: weight entries, health entries and medication courses including finished ones, each course with its full dose history of timestamp, amount and giver, and the export span used to default the range control (EXP-1, EXP-2).
- [ ] 2.11 [rust-backend] Implement PDF generation of the selected history as a formatted, vet-readable document, off the main thread, covering weight, health and medications, with no schedule type and no empty dose history able to fail it and with German text rendered correctly (EXP-1, EXP-4, D4.4).
- [ ] 2.12 [rust-backend] Implement the raw CSV export for the same range: medications and doses written to dedicated files separate from each other and from the entry files, the dose file carrying timestamp, amount and giver for every dose, values written as stored (EXP-2).
- [ ] 2.13 [rust-backend] Implement export robustness across all four schedule types with and without recorded doses, presenting each course through P5's existing human-readable schedule summary rather than a second implementation (EXP-4, MED-4 reused).
- [ ] 2.14 [rust-backend] Implement the export file boundary: produce the files into a device-local export location with a defined lifetime, return them for handoff, present no file when the export did not complete, report a failure through P0's cause-carrying error surface, and give the product no path that sends an export anywhere (EXP-1, EXP-3, D4.9).
- [ ] 2.15 [rust-backend] Implement the language preference: store System/Deutsch/English as a device-local value, resolve the effective language once at launch from the stored value or the device language, and never change the running session's language (SET-3, D4.8).
