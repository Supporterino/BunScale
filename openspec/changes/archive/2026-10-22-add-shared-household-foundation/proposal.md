# add-shared-household-foundation

> Phase **P0 — Foundation** of the BunScale reimplementation.
> Source of truth: `docs/BunScale-Reimplementation-Requirements.md` and
> `docs/BunScale-Reimplementation-User-Stories.md`.
> This change owns 18 product requirement IDs and no others, plus the 8 requirement IDs
> (TOOL-1 … TOOL-8) of the `project-toolchain` **enabler** capability described below.

## Why

BunScale's product promise is a *shared* record of care: several people, each with their own
account, editing one set of rabbit data. Historically that is exactly where the product failed
(IMP-2 — rabbits disappearing, invitations not acceptable, the owner missing from the member
list). Everything else in the product — weight, health, medications, photos, export — is only
worth building on top of a sharing and persistence foundation that is correct, observable and
honest about failure.

The reimplementation is greenfield: there is no code. This change establishes the smallest
foundation that can be proven end to end:

- a person can create and hold households, with exactly one active (HS-1 … HS-4, DM-3);
- household data is one logical collection per household with no duplicates and last-write-wins
  convergence (SYNC-1, SYNC-5);
- writes are honest: saves require the shared service to be reachable and are never faked
  (SYNC-2, NFR-1, NFR-8);
- reads degrade sensibly: previously loaded data is shown when the service is unreachable and an
  explicit "connectivity required" state replaces misleading empty data (SYNC-3);
- the two per-device preferences needed from day one exist: the display weight unit and the
  read-only account name in Settings & Profile (SET-1, SET-2, SET-4).

**The workspace itself does not exist yet.** The repository holds requirements, user stories and the
agent kit only — no package manifest, no Rust crate, no frontend — while the `definition-of-done`
gate, the `AGENTS.md` command table, the tasks below and all six sibling changes assume one. The
product owner therefore folded a **section 0 workspace scaffold** into this change (`tasks.md`),
covered by the new `project-toolchain` capability (TOOL-1 … TOOL-8). Those requirements have no
counterpart in either source document: both describe product behaviour and silently assume a
codebase. They are a deliberate **enabler** addition — they add no product behaviour and modify no
existing requirement — and they are what makes the rest of P0 buildable and verifiable at all.

Section 0 does not hand-write that workspace. It opens with **one bootstrap task owned by
`architect`** that generates the `src-tauri/` baseline with the official Tauri v2 CLI (`cargo
install tauri-cli --version "^2" --locked` → `cargo tauri init --ci` → `cargo tauri ios init` →
`cargo tauri capability new`) and commits it as one commit of generated output; every later
section-0 task refines what the generator produced. `tauri init` — documented as *"Initialize a
Tauri project in an existing directory"* — is the right utility (it creates only `src-tauri/` and no
frontend), while `create-tauri-app` is not: this repository is non-empty and its React template
would be discarded for lacking TanStack Router file-based routing, Query, vitest/Playwright, lint
tooling and `tauri-specta`. See `design.md` D0.11. `cargo tauri icon` is deliberately not part of
that pass: the app mark is drawn from the design-system tokens and generated by `frontend-ui` in
section 0 (`design.md` D0.19), so the bootstrap ships Tauri's default iconset only until that task
replaces it.

**Why first:** every later phase (rabbits, weight, health, medications, photos, reminders,
export, performance) reads and writes through the contract, storage boundary and error surface
defined here. Getting the write model, the collection identity and the failure semantics right
once is cheaper than retrofitting them onto six capabilities.

## What changes

New capability surface (specs are technology-agnostic; "the shared service" and "the account"
are the only names used for the sharing mechanism — see decision D6):

| Capability | Requirements added | Substance |
|---|---|---|
| `household-sharing` | HS-1, HS-2, HS-3, HS-4, DM-3 | Household creation with a name, first-run onboarding shown once, multiple households with one active, household management from Settings & Profile |
| `sync-and-offline` | SYNC-1, SYNC-2, SYNC-3, SYNC-5 | One logical collection per household, reachability-gated writes, loaded-data reads, last-write-wins convergence |
| `settings-profile` | SET-1, SET-2, SET-4 | Settings entry point from the dashboard, read-only account name with fallbacks, per-device display weight unit |
| `product-quality` | NFR-1, NFR-2, NFR-3, NFR-8 | Connectivity model, conflict resolution, privacy and diagnostics, cause-specific failure reporting |
| `data-integrity` | NFR-10, DM-6 | Household-scoped isolation and canonical storage at the storage boundary, absolute-instant timestamps |
| `project-toolchain` | TOOL-1 … TOOL-8 | **New capability, enabler only.** Section 0 workspace scaffold: a buildable workspace whose full gate passes on a clean checkout, app boot on the iOS simulator and macOS, reproducible `src/bindings.ts` and `src/routeTree.gen.ts` with CI drift checks, a two-baseline test harness, a recorded design system, and exactly pinned iOS+macOS dependencies |

The `project-toolchain` capability is new in this change and adds no product behaviour. Its
requirements carry no source-document ID — the source documents specify no toolchain — and are a
decision of the product owner, stated as such in the delta's header
(`specs/project-toolchain/spec.md`).

Supporting work: the P0 IPC contract with typed stubs in `src-tauri/src/ipc/`, the capability /
CSP / scope / entitlement changes the chosen sharing mechanism needs, the frontend data layer
(bindings wrappers, query keys, active-household state, service-status store), the P0 screens
(onboarding, dashboard shell with the gear control, Settings & Profile, offline and save-failure
states), and tests at unit, component and E2E level.

### Settled decisions this change implements

- **D1 — Write model: connectivity-required saves.** SYNC-2, SYNC-3, NFR-1 and NFR-8 stand as
  written. Offline dose logging (US-MED-23) is **dropped**; IMP-1 is closed. There is no local
  write queue, no optimistic write and no reconciliation of pending writes.
- **D2 — Sharing model: owner-dependent sharing.** The household records its owner member. No
  ownership transfer and no backup/restore flow. HS-13 remains an **accepted risk** (documented
  in `add-household-sharing-hardening`, P3); IMP-8 stays uncommitted backlog.
- **D6 — Technology-agnostic.** Nameless shared service throughout the specs. The concrete
  mechanism is selected and justified by `architect` in `design.md` (task 1.1) before any
  backend work starts.
- **D3 (unified reminders), D4 (fresh start, no data import) and D5 (chart baseline band out)**
  do not affect P0; they are recorded in the changes that own them.

## Impact

- **Scaffold bootstrap:** section 0 opens with one `architect` task that installs the Tauri v2 CLI and
  runs the generator pass (`tauri init --ci` → `tauri ios init` → `tauri capability new`), committing
  the generated `src-tauri/` baseline as one commit marked as generated output. `architect` gains
  shell access for `cargo install tauri-cli *` and `cargo tauri *` for that task. Everything after it
  refines the generated baseline: the generator does not reduce the exact-pinning work (TOOL-8), the
  frontend stack, the `tauri-specta` pipeline, the test harness, the lint tooling, the design system
  or CI, all of which stay hand-owned (`design.md` D0.11). `tauri init` generates no frontend, so
  there is no template to delete. The bootstrap is **not blocked**: the app identity is settled
  (`com.bunscale.app` / `BunScale`, D0.15), the icon step has moved out of it to the `frontend-ui`
  task 0.22 (D0.19, so 0.1 ships Tauri's default iconset only until that task replaces it), and the
  `ios init` ordering risk is settled by D0.20 with a documented fallback. Section 0 also carries one
  `apple-native` task (0.7) that measures the iOS/macOS deployment floor from the installed SDKs
  (D0.16).
- **New Rust surface:** `src-tauri/` from nothing — `Cargo.toml`, `build.rs`, `src/main.rs`,
  `src/lib.rs`, the `src-tauri/tests/` integration harness, `src-tauri/src/ipc/` (commands, events,
  shared types), `src-tauri/tauri.conf.json`, `src-tauri/capabilities/`, household domain and state,
  the storage boundary and local copy, diagnostics redaction.
- **New frontend surface:** the frontend workspace itself (`package.json`, `index.html`,
  `tsconfig.json`, `vite.config.ts`, `src/main.tsx`), `src/styles/` and `src/components/ui/` (design
  system), `src/test/` and `e2e/` (harness), the Playwright/vitest/lint configuration,
  `.gitignore`, `src/routes/` (onboarding, dashboard shell, settings), `src/features/households/`,
  `src/features/settings/`, `src/features/sync/`, and the generated `src/bindings.ts` /
  `src/routeTree.gen.ts` (regenerated, never hand-edited).
- **New CI surface:** `.github/workflows/ci.yml` on `macos-latest` running the same gate as
  `definition-of-done`, including both generated-artefact drift checks. No signing, no TestFlight,
  no release job in this change.
- **Security surface:** the scaffold's baseline capability set, CSP, `Info.plist` usage strings and
  macOS entitlements (via `tauri-security` only); the sharing mechanism later introduces network
  egress, so `src-tauri/capabilities/`, CSP, scopes and entitlements change again — also via
  `tauri-security` only.
- **Dependency surface:** section 0 is the point where every dependency is introduced — the Tauri v2
  Rust crates plus `tauri-specta` + `specta` (pinned to matching exact versions, release candidate
  accepted per D0.18), the frontend runtime (`@tauri-apps/api`, `react`, `react-dom`, TanStack Router +
  Query), and dev-only tooling (`@tauri-apps/cli`, vitest, Testing Library, Playwright WebKit, Biome).
  Biome is the one lint and format tool (D0.17). The sharing mechanism's client
  library is added later, justified in `design.md`. **No Tauri plugin is added by section 0**, so
  there is no plugin whose platform support needs confirming; everything pinned above is usable on
  both Phase 1 platforms — the Rust crates are platform-neutral, only `@tauri-apps/api` is
  Tauri-specific, and the other runtime packages ship platform-neutral JavaScript, while the native
  binaries that do exist belong to host/CI tooling, which publishes a macOS/arm64 variant and never
  ships in the app.
- **Risk carried forward:** sharing correctness (IMP-2) is the primary risk of this phase and is
  the reason invitation/acceptance hardening is scheduled early (P3) rather than late; a broken or
  unpinned scaffold would block every other phase, which is why TOOL-1 makes the gate itself a
  requirement.
- **Not in this change:** rabbits, weight, health, medications, photos, export, reminders,
  invitations and member management, language override (SET-3), any data import, and any release or
  distribution work — no signing, no TestFlight, no notarisation and no updater. Android, Windows
  and Linux stay unbuilt (the scaffold is only `cfg`-clean for them).

## Dependencies

This change has no predecessor change. It does have an **internal prerequisite**: section 0
(workspace scaffold), covered by the `project-toolchain` capability (TOOL-1 … TOOL-8), must complete
before any task from section 1 onwards can run. Everything the later sections and the six sibling
changes assume — the gate commands in `definition-of-done`, `bun run gen:bindings`, the route tree,
the two-baseline test harness, the pinned dependency set and the recorded design system — is created
there. Inside section 0 the order is `architect` → `tauri-security` / `apple-native` / `release-ci` →
`rust-backend` / `frontend-logic` → `frontend-ui` → `test-engineer`, and `architect`'s first action
is the CLI bootstrap that generates the baseline everything else refines (`design.md` D0.11). Phase
labels, task numbering and archive order are unchanged by this: the scaffold adds section 0, it does
not become a change of its own.

Six sibling changes depend on it:

| Phase | change-id | Depends on P0 for |
|---|---|---|
| P1 | `add-rabbit-weight-core-loop` | storage boundary, collection identity, save/read semantics, display unit, failure surface |
| P2 | `add-health-and-photo-history` | collection identity, household scoping, local photo copy semantics |
| P3 | `add-household-sharing-hardening` | household/member model, owner member, live-update subscription point |
| P4 | `add-vet-export-and-reminders` | read path, error surface, per-device preference storage |
| P5 | `add-medication-tracking` | household collection, member identity for dose givers, connectivity-required saves |
| P6 | `add-read-path-performance` | the read path and cache boundaries introduced here |

The phases are listed by phase id, which is not the archive position (see below).

**Archive order.** Because each later change modifies capability specs opened here, archives MUST
run in the resolved order **P0 → P1 → P2 → P3 → P5 → P4 → P6**, i.e. `add-medication-tracking`
(P5) archives **before** `add-vet-export-and-reminders` (P4).

That order was resolved deliberately: the naive `P0 → P1 → P2 → P3 → P4 → P5 → P6` sequence was
circular, because P4's export needs the medication model while the medication reminders need the
reminder mechanism P4 introduces. Archiving the medication model first breaks the cycle, so P5
precedes P4.

Archiving out of order (or in parallel) leaves `openspec/specs/` with deltas applied against text
that does not yet exist.
