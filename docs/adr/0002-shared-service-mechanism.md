# ADR 0002 — Shared service mechanism: where the shared service runs and how it is written to and read from

- **Status:** Accepted
- **Date:** 2026-10-19
- **Sources:** `docs/BunScale-Reimplementation-Requirements.md` (§6: HS-12, SYNC-1–SYNC-5; §7: NFR-1, NFR-2, NFR-3, NFR-8; §10), `docs/BunScale-Reimplementation-User-Stories.md` (§13; EP-2, EP-7 (US-MED-23), EP-12), `docs/adr/0001-reimplementation-scope-decisions.md` (D1, D2, D6 and its "Open follow-up required from the P0 `design.md`"), `openspec/changes/add-shared-household-foundation/design.md` (D0.1, D0.2, D0.5, D0.6, D0.7, D0.12, D0.13, D0.14, D0.21), `openspec/changes/add-shared-household-foundation/specs/sync-and-offline/spec.md` (SYNC-1, SYNC-2, SYNC-3, SYNC-5), `openspec/changes/add-shared-household-foundation/specs/product-quality/spec.md` (NFR-1, NFR-2, NFR-3, NFR-8), `openspec/changes/add-shared-household-foundation/questions.md` (Q25)
- **Deciders:** architect (the mechanism selection in task 1.1, the reading the NFR-3 criterion is applied on, and this record in task 1.2); product owner (the framing of ADR 0001 D6 and the scope decisions it carries)

## Context

ADR 0001 D6 deliberately left the shared service unnamed: the capability specs keep saying "the shared service" and "the account", and the concrete mechanism was deferred to the P0 `design.md`, with a written list of five follow-ups it had to satisfy (platform support, identity, storage accounting, failure taxonomy, privacy). That deferral is what **this ADR closes**. This is the durable decision record in which the vendor is named; the task-1.1 analysis behind it, including the criterion-by-criterion test, lives in `design.md` D0.7 and `questions.md` Q25 names the vendor in recording the account gap, while the capability specs stay agnostic (D6) and no capability spec may pre-empt this record.

The mechanism had to satisfy two independent checklists: ADR 0001's five follow-ups, and the six interaction criteria fixed in `design.md` D0.7 — (1) address a household collection by an opaque, stable id; (2) read the collection and per-item changes since a marker; (3) write an item with a client-supplied version for last-write-wins; (4) report availability and account state in a way that maps to cause codes; (5) report allowance exhaustion as its own condition, distinct from rate limiting and from a generic write error (D0.12); (6) accept a client-supplied idempotency key and deduplicate on it (D0.14). The six criteria were fixed **before** the selection so the choice is auditable, and the criterion-by-criterion test against the components below is recorded in `design.md` D0.7 — this ADR states the decision, its scope and its cost, and points there rather than duplicating it line by line.

Two consequences of that ordering shape the rest of this record: the write model (W1, connectivity-required) and the read model (R1, loaded data) are decided **here** because they are what the mechanism has to serve, and the mechanism must not be re-litigated from them. The requirements that bound them are SYNC-2/SYNC-3 (saves require a reachable service and a valid account; reads use previously loaded data), NFR-1, NFR-2 and NFR-8, all of which stand as written.

## Decision

### M1 — Selected mechanism: the self-hosted, product-operated Supabase stack

**The shared service is the open-source Supabase distribution, deployed by the product on infrastructure the product controls.** The hosting provider supplies machines; the product operates the service software, its schema, its access policy and its data plane.

| Role | Component |
|---|---|
| Collection store, source of truth | **PostgreSQL** with **row-level security** — one logical collection per household; `(household_id, item_id)` primary key makes "exactly one copy" (SYNC-1) a store invariant rather than a client-side check |
| Account | **Supabase Auth (GoTrue)** — the JWT's `sub` is the stable account id; the app never holds the service-role key, so every request carries the person's JWT |
| Read/write surface | **PostgREST plus product-authored SQL functions** — `household_changes(household_id, since_change_seq)` for the collection and its per-item changes, `save_item(…, writer_id, request_id)` for version-ordered writes |
| Rate limiting | **The stack's own gateway (Kong)** with its rate-limiting plugin, reporting `429` with `Retry-After` |
| Client | **Rust over HTTPS with `reqwest`** (rustls, no native TLS binding), per D0.7's rule-6 justification — no Tauri plugin, no Apple-only API |

**Scope of the decision.** It fixes the interaction shape — one shared collection per household, per-item last-write-wins on a client-supplied version, a resumable change feed, per-owner allowance accounting, server-side idempotency — and the deployment shape above. It does **not** fix the physical schema layout (D0.7 permits task 2.3 to split the rows per kind, provided every household-scoped row keeps `household_id`, the version tuple and `change_seq`), the allowance value (deployment configuration, not a mechanism choice — D0.7 criterion 5; D0.12 fixes only that it is per owner and distinctly reportable), or the stack's Realtime component (available for P3's live-update subscription point, explicitly outside the P0 contract).

**The cost, stated plainly.** Criteria 3, 5 and 6 are met by product-authored SQL — constraints, functions and a request ledger — not by a feature of a closed API. That is precisely the control a closed backend cannot give, and it is why this stack is selected over one. The price is operational: **the product must run PostgreSQL, Auth, PostgREST and the gateway.** That deployment lives outside this app repository and outside this change's gate.

**Licensing.** The components are open source, self-hosted by the product, each under its own licence — PostgreSQL under the PostgreSQL License; Supabase Auth (GoTrue) and PostgREST under MIT; Kong and the Supabase distribution around them under Apache-2.0. The deployment task must confirm each component's licence against the version it actually deploys rather than relying on this line. None is linked into the iOS or macOS binary and none adds a platform constraint to the app. The mechanism's only required new dependency in the app itself is the Rust HTTPS client justified in D0.7; it is **not** present yet — section 2 adds the exact pin, with that justification, in the task that first puts it in `src-tauri/Cargo.toml` (D0.8/TOOL-8).

**The NFR-3 reading, recorded because it decides the row that was rejected for it.** "The product's own shared service" is read as *the product operates the service software, schema, access policy and data plane*, **not** as *the product writes every line of it*. A managed backend in which the vendor operates the database and holds the data — Supabase Cloud, Firebase, CloudKit — fails that reading however convenient it is; the same open-source stack deployed by the product satisfies it. This is the test a later infrastructure change must keep passing, and it is the reason the vendor-operated deployment of the **same** stack is rejected on privacy alone rather than on capability. It also has a narrow, load-bearing corollary: the service origin is **not** a webview network surface, because the calls are made in Rust, so the strict CSP owed by D0.21 needs **no** `connect-src` entry for it and task 1.4 must not add one.

### W1 — Connectivity-required write model (implements ADR 0001 D1; `design.md` D0.1)

Writes are attempted **only** while the shared service is reachable and the account is valid. There is **no local write queue, no optimistic write and no deferred reconciliation**; conflicting local edits are not merged later, because nothing is kept locally to merge. A write that the service refuses is surfaced with its **specific cause and is retryable by the person** — the failure is never silently discarded and never presented as saved (SYNC-2, NFR-8, and the single typed failure surface of D0.6). Retrying is safe by construction because every state-changing command carries the client-generated `request_id` the service deduplicates on (D0.14).

The accepted cost is that **care logging while offline is impossible**, so the UX must make the connectivity requirement obvious *before* a person invests effort in a form; offline dose logging (US-MED-23) is dropped. Reads are unaffected by this model — they are served from the locally kept copy (R1 below; `design.md` D0.2). The mechanism is what makes the model enforceable rather than advisory: with the RPC as the only write path, a write cannot be recorded locally and later presented as saved.

### R1 — Loaded-data read model (implements SYNC-3; `design.md` D0.2)

The device keeps a **local copy of each household collection it has loaded**, and reads **always resolve against that copy first**; a start or foreground return **with connectivity refreshes it** (SYNC-3, NFR-1). "Nothing was ever loaded on this device **and** the service is unreachable" is a **distinct state with its own surface — never an empty list and never stale data presented as current**.

P0 fixes only the **boundaries**: where the cache lives (`src-tauri/src/storage/`) and what a refresh replaces (the collection the feed describes, through `src-tauri/src/sync/`). Serving the copy first, batching the refresh and invalidating only affected data is the subject of `add-read-path-performance` (P6, NFR-7). Naming the boundary now is what lets P6 improve the behaviour without moving it — and the service's side of the boundary is the change feed, not a per-device row: a device can be rebuilt from `household_changes(…, 0)`, which is why the feed is the cache's contract.

## Consequences

- **The product operates a data plane.** PostgreSQL, Auth, PostgREST and the gateway must be run, patched and backed up by the product. That deployment is **outside this repository and outside the P0 gate**: no P0 task boots the service and the gate's E2E layer mocks IPC. A **live deployment is a precondition only for the task or release that first needs a real write**, and that task must record it — nothing in P0 assumes it exists. The same task also provisions the first service account, because P0 has no sign-in flow.
- **The gate does not cover the SQL that implements the decision.** Because the service is mocked, the SQL behind criteria 2, 3, 5 and 6 — the change feed, the LWW comparator, the allowance check and the idempotency ledger — is **not exercised by the P0 gate, as specified**. The deployment change must test those functions against a real PostgreSQL **before** the first release that writes through them. This is the largest unverified surface this decision creates, and it is recorded rather than smoothed over.
- **`request_id` lifetime and retention (D0.7 criterion 6; the semantic reading is D0.14).** The client keeps a `request_id` for **24 hours** after the last attempt **or** until the operation succeeds — whichever is longer. The service retains the ledger for `REQUEST_ID_RETENTION` = **30 days**, comfortably longer than any retry the product offers, so retention stays bounded without reopening the duplicate window. `CommandError.request_id` is therefore semantic, not diagnostic: it names the operation whose identity must not be duplicated.
- **Deterministic LWW is only as truthful as the devices' clocks.** The service stores the client's `updated_at` beside a server `received_at` for diagnosis and applies a **bounded skew guard** on the version marker, so one future-dated device cannot win forever; the obligation belongs to the **section-2 service schema work**, alongside the LWW write path it protects. The LWW `updated_at` is the item's version marker, distinct from any user-supplied domain timestamp, which remains stored unchanged (D0.5).
- **A hard delete must be a tombstone write**, not a vanished row, or the change feed cannot report the removal to other devices.
- **The bounded times stay client-side and concrete (D0.13):** `SAVE_ATTEMPT_TIMEOUT` 15 s, `REACHABILITY_PROBE_TIMEOUT` 5 s, `OFFLINE_FAILURE_THRESHOLD` 3 consecutive failures. The `timeout` cause is a first-class, bounded cause rather than a placeholder, and the probe checks service reachability and account validity separately so `ServiceStatus.account_valid` is a fresh outcome rather than a cached guess.
- **No Tauri plugin, and no CSP widening.** The calls originate in Rust, so `tauri-plugin-http` is not needed and the strict policy of D0.21 needs no `connect-src` entry for the service origin; a future webview path to the service reopens that bullet and owes the entry with its own justification.
- **One release-time platform obligation.** The macOS App Sandbox set that ships with the first signed or distributed build must include `com.apple.security.network.client`; the change that enables the sandbox owes that entitlement then, authored by `tauri-security` (D0.21).
- **P0 has no sign-in screen (Q25, open).** The mechanism supplies the account (GoTrue email OTP is the intended method when the flow lands, and the refresh token belongs in the platform Keychain, never in the local data cache), but **no P0 task implements sign-in or account acquisition**, and no task owns the flow itself. The first live account is an operator step in the deployment task above, not a user-facing flow. Q25 records the gap with its needed owner and phase.
- **Reversal is a deployment change, not a schema change.** Because the interaction criteria are met by the PostgreSQL schema and product-authored SQL rather than by a vendor feature, moving onto a vendor-operated deployment of the same stack would leave the schema and functions intact; it must nevertheless be recorded as an explicit NFR-3 exception rather than inferred.

## Alternatives considered

| Alternative | Outcome |
|---|---|
| **Apple CloudKit** (native framework; a shared record zone per household) | **Rejected — fails criterion 3, criterion 6 and NFR-3.** Its only optimistic-concurrency primitive is the server-assigned `recordChangeTag`, so a concurrent save returns `serverRecordChanged` for the client to retry: conflict retry, not deterministic last-write-wins on a client-supplied version. It has no idempotency-key ledger, so a re-issued modify is not deduplicated. And the data lives in the user's or owner's iCloud under Apple's terms, which is not the product's own service. It does meet criteria 4 and 5, so the rejection is specific rather than blanket. |
| **Firebase / Cloud Firestore** | **Rejected — fails criteria 3, 5, 6 and NFR-3.** Firestore's preconditions are the server-assigned `updateTime`, so last-write-wins is by server commit order. Quota exhaustion and rate limiting both surface as `RESOURCE_EXHAUSTED`/`429` with no reliable distinction, and the quota is project-level, not the per-owner allowance HS-12 requires. There is no client idempotency key or dedup ledger. Google operates the data plane. |
| **Firebase Realtime Database / any other closed BaaS** | **Rejected on the same criteria as Firestore** — no client-version LWW comparator, no per-owner allowance distinct from rate limiting, no server-side idempotency key — plus NFR-3's data-plane requirement. Listed so the rejection is not read as Firestore-specific. |
| **Supabase Cloud** (the same stack, vendor-operated) | **Rejected on privacy alone — NFR-3 — not on capability.** Criteria 1–6 are met by the same schema and functions, and it would remove the operational cost, but the vendor would operate the data plane holding health and weight data, which is the line this ADR draws. A dedicated project and a processing agreement do not change who operates the database. If the product owner later accepts that trade, it is a deployment change to this decision, recorded as an explicit NFR-3 exception rather than inferred. |
| **Custom Rust service** (axum + `sqlx` over the same PostgreSQL schema) | **Not rejected on a criterion; rejected on cost and risk.** It meets the six criteria by construction and keeps the data plane in-house with no Supabase component, but it must build identity itself — account issuance, token refresh, JWT verification, RLS enforcement and the HTTP data API — as a second bespoke codebase, re-implementing the parts most likely to be wrong while the chosen stack supplies them as maintained components over the same PostgreSQL. It remains the fallback if the stack's operational shape later binds. |
